# UVLM 单工况耗时诊断与提速(2026-07-09)

## 0. 问题(用户裁定:速度最优先)

nc12 回放单工况 45-60 分钟(f1.4 达 1.5-2.5h)——192 面板的低阶方法付出了高阶 CFD 的价钱。
用户问:GPU 没利用好还是算法缺陷?答:**实现层缺陷为主,三处病灶,全部量化定位。**

## 1. 基线剖析(RTX 4090D,nw=11,520 生产峰值,ms/次)

| 环节 | 耗时 | 根因 |
|---|---|---|
| `_convect_wcore`(自由尾迹对流) | **384** | fp64 N² 直和;GeForce fp64 吞吐 = fp32 的 **1/64**(1.3 vs 83 TFLOPS) |
| `batched_dense_solve` 192² | **150** | `dim=B` 启动,**B=1 → 整个 O(N³) LU 在单 GPU 线程串行**(为多环境 co-design 批量设计,单批病态) |
| `_rhs_moving_wcore` | 142 | **dim=192 线程**(6 warp)× 11.5k 串行内环 → 占用率 ~1%,延迟绑定 |
| `_col_wake_wcore` | 143 | 同上 |
| Python 闭合/簿记等 | <5% | 非瓶颈(之前的怀疑排除) |

端到端 445 ms/步 × spc(=15·U·nc/f)× 4 周期 × 柔/刚两遍 = 小时级。预算完全闭合:
convect 34% + solve 34% + rhs/col 31%。

## 2. 修复(三项,零物理改动)

1. **fp32 诱导算术**(`wake_f32=True` 默认开,False=旧 fp64 逐位路径):三个 N² 核的
   Biot-Savart 算术转 fp32;**全部状态保持 fp64**(尾迹位置更新 Pd + fp64(v)·dt,防止
   3000 步位置漂移;rhs 基项 −(V∞−V_body)·n 保持 fp64 精确)。fp32 求和 11.5k 项的
   相对误差 ~1e-6 ≪ ±0.15N 跑间噪声带。
2. **chunk 并行化**:rhs/col 从 192 线程 → 192×64=12k 线程(源环按 chunk 条带分,fp32
   部分和 `wp.atomic_add` 进 fp64 输出)。原子加引入 1e-15 级次序非确定性——本已存在
   (跑间带 ±0.15 由 LEV 门限放大所致)。
3. **solve 宿主机路径**:`batched_dense_solve` 增加 B≤4 分支走 `np.linalg.solve`(LAPACK
   dgesv,与 GPU 核同为部分选主元 LU,数值等价),<1ms 含传输;B 大保留 GPU 批量路径。
   所有调用方(含 S5 耦合 provider)自动受益。

## 3. 验证与结果(A/B,2026-07-09)

微基准(nw=11,520,ms/次):

| 核 | fp64 旧 | fast 新 | 加速 |
|---|---|---|---|
| convect | 384 | 20.6 | 18.6× |
| rhs | 142 | 0.19 | 747× |
| col_wake | 143 | 0.19 | 752× |
| solve 192² | 150 | 0.39 | 385× |

- 端到端 nc12/spc720/1周期:445.0 → **25.5 ms/步(17.5×)**;L/T = +6.006/+1.552,
  与 fp64 基线小数点后三位一致(1 周期混沌未放大)。
- kelvin 冒烟(K0 nc4 U8/f2.0 ×4周期):fast L=+5.890/T=+1.159 vs fp64 (+5.996/+1.121),
  差 (0.106, 0.038) 在 ±0.15 跑间带内 PASS(4 周期 LEV 门限混沌放大所致,与已测跑间
  非确定性同量级,非系统偏差)。
- rhs f32-vs-f64 逐元素:max 3.7e-7 绝对 / 4.7e-8 相对。

**单工况新成本(估)**:nc12 回放 f2.3 ≈ 2-3 分钟(原 ~50 分钟);f1.4 ≈ 4-6 分钟
(原 1.5-2.5h);nc4 诊断 ≈ 10-30 秒(原 3-5 分钟)。
**注**:S5 耦合录音走独立代码路径(newton_pc provider),只自动吃到 solve 修复;
其余两处如需提速需单独移植(二期)。convect 现占剩余成本 ~80%,tile 化可再 ~3-5×。

## 4. 已识别未做(二期,按收益排序)

- **回放尾迹截断**:回放 wake_rows=spc(整周期),耦合录音验证过 K=18 行就够——但生产
  图口径当年用全尾迹,截断需对 ±0.15 带单独验证后才能动。潜在再 ~2-4×。
- **CUDA graph capture**:消每步 ~30 次 kernel launch + Python 开销;需先清理每步分支。
- **convect tile 化**(shared-memory 协作加载源块):fp32 后若 convect 仍主导再做。
- 非 wcore 路径的 chunk 化(生产不走,已有 fp32 串行版,~5-10× 够用)。

## 5. 与 FLOWVPM 的对照(用户问询)

FLOWVPM 的 GPU 加速 = tiled 直和 + FMM 远场。我们 N~1.2 万环远低于需要 FMM 的规模
(10 万+),tiled/fp32 直和即可;Warp 的可微性(wp.Tape)只关反向,与前向速度无关——
真正相关且此前未用的是 fp32 算术路径与(二期)tile 原语/CUDA graph。
