## 2. 为什么成立

- **单元独立性（实测，非读代码）**：只喂 element 0 的单位方向 → 作用量非零项恰好 96、支撑正好是 element 0 的块；喂 element 0+31 → 192 项两块；`action(0+31) == action(0)+action(31)` **`torch.equal` 为真**。
- **每批代价与方向稀疏无关**：局部布局 176.9 ms/批 vs 全局布局 176.5 ms/批。所以省的不是"每批更便宜"，而是**批数 47 → 2**（96 个局部方向 = 64 + 32）。
- 全局阵由 `K[g(e,i), g(e,j)] += K_e[i,j]`、`g(e,n) = connectivity[e,n]*6 + c` 散加得到。

## 3. 三次踩坑（都由对照测出来，不是读代码看出来的）

1. **线性化必须按批扩展**。element operator 按 batch 索引 linearization；传 batch=1 的原样张量与 96 方向的批一起用会越界读，结果量级 1e10（而正确值 1e5–1e7）。修正：与生产探测一样 `expand((count,)+shape).contiguous()`。
2. **`start = dof` 不能"跳过" for 循环**。第一版把 `start` 设在 `for` 之前，循环首轮立即重绑成 0 ⇒ 列探测照跑并覆盖同样的值。**digest 逐位相同恰恰掩盖了这一点**（两条路径给出同一矩阵），只有步价（5.416 vs 5.346，没变）暴露了它。改成真正的 `if/else` 后才有 4.033。
3. 与**陈旧参考阵**比较会得到 5.2e-7 的假差（同一状态下的列探测与存储阵本身差 1.1e-7）。真对照必须在同一 `linearization` 上现场跑一次列探测。

## 4. 为什么是逐位相同（而不是我先前预估的 ~1e-14）

散加以元素顺序累加，与 `q16_local_to_global_kernel` 的 node-occurrence 求和顺序一致，因此 2976² 全阵逐位相等 —— 我此前"必然非逐位、只能容差验收"的判断是**错的**。这次测量把整条链的"全程位级等价"属性保住了。

## 5. 边界

- 逐位相等在**两个状态**上验证：A16 步 1 后的状态（`/tmp/p03_gate.py`，两条路径直接对比）与 150 步全长运行的 digest 链（19 次刷新）。
- 只在 A16 网格（dof 2976、50 单元、局部 96）上验证；其他网格（如 Yamano 5×3）未跑，但方法是网格无关的（`element_count`/`Q16_DOF_PER_ELEMENT` 从算子取）。
- 峰值显存：96 方向的局部作用量 (96, 50, 96) = 3.7 MB + 每批 expanded 线性化（64 × 24.9 MB ≈ 1.6 GB，与列探测同量级）。
