## 3. 三条新结论

**① 稠密解不再是主项。** `dense_solve` 386.4 ms/步 = **6.8%**。S1 之前它是 105–160 次分解 × 21.65 ms = 2.3–3.5 s/步。**结构侧剩下的 ~1492 ms/步（非稠密部分）+ `tangent_refresh` 1382 ms/步 = 2874 ms/步 = 50.6%**，比整个气动侧（1860 ms = 32.7%）还大。这正是此前台账里"未归因的 2.0 s/步结构开销"，现在至少分成了两块。

**② 环求和与粒子 BS 同量级。** `ring_BS` 800.0 ms（47.95 次/步）vs `particle_BS` 965.0 ms（26.95 次/步）。此前台账只有粒子 BS 的对数（9.63e9），环侧完全未计；按耗时看环侧是气动侧的 43%。主计划 S5 的"混合精度 BS"只覆盖粒子侧，因此最多触及气动部分的 57% 量级。

**③ 阻塞式主机读取次数庞大。** 每步 **3641 次 `Tensor.item` + 2909 次 `wp.synchronize_device` = 6550 次**，测得等待 2401.6 + 1025.1 = 3426.7 ms/步。这个数是**包含它所等待的 GPU 工作**的，因此是上面相位时间的分解，不能与它们相加（我第一版把它加上去，得到 159% 的假闭合）。

## 4. 测量边界（必须随表一起引用）

1. **重叠标签**：`advance_wrk3` 的三个 RK3 级里既有 `velocity_self_cuda`（即 `particle_BS`），也有位置拷贝与环影响；`ring_BS` 的一部分也在 `advance_wrk3` 内。这三者的 "exclusive" 列无意义，表里已标 `(overlaps)`，只作 inclusive 读。
2. **含主机同步的相位会吸收此前排队的工作**。`tangent_refresh` 只有 0.13 次/步（≈19.5 次/150 步）却记到 1382 ms/步，即**每次刷新约 10.6 s** —— 这个数包含了它内部同步点之前排队的所有工作，不能读作"刷新本身的计算量"。要拆开需要在该函数内部按其同步点分段计时。
3. 单工况（A16）、单窗口（步 1–150）、单精度（fp64）、单设备（4090 D）。
4. `Q16NativeAuthorEndpointLoad.assemble` 未插桩（类属性名不匹配），载荷组装因此被算在 `propose`/`struct_step` 之外或之内未分离。

## 5. 对 10 min 目标的直接含义（只列算术）

当前 5.683 s/步 × 2100 步 = **3.31 h**。目标 600 s / 2100 步 = **0.286 s/步**，差 **19.9×**。

| 块 | 现状 ms/步 | 已知/待测的杠杆 |
|---|---|---|
| 结构非稠密 `struct_step` | ≈1492 | **未归因**（下一个测量目标） |
| `tangent_refresh` | 1382 | 0.13 次/步；含同步吸收，需内部拆分 |
| `velocity_force` | 527.5 | S3 计划缓存冻结端点几何（`surface.evaluate` 每次重跑，位置量逐位相同） |
| 气动 `propose` | 1860 | S4/M6 复用对流场（2.98 → 1，约 3×），但 `_external_velocity` 依赖 `geometry.rings` 与 `trial.gamma_bound`，属滞后耦合 |
| `dense_solve` | 386 | S1 已做完；1B（每外步 1 次分解）还能再省 (10.07−1)×21.65 ≈ 196 ms |

若结构非稠密与 `velocity_force` 都能压到接近 0、`tangent_refresh` 压到 0、气动做 3× 复用（1860 → 620）、`dense_solve` 做 1B（386 → 190），则总价约 **0.62 + 0.19 ≈ 0.81 s/步**，仍比 0.286 高 2.8×；差额必须来自气动侧的每对吞吐（S5）或粒子数/对数削减。这些是算术，不是结论。
