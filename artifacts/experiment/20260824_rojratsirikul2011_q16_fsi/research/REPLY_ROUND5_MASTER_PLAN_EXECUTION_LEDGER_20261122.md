## 1. S1：判断准确，但还有第二个 bug（计划没料到）

计划写的 `q16_structural_solver.py:414, 1540` 单槽驱逐**成立**，而且它对"`dgetrf` 由 29 → 10 次/步"的估计**精确命中**：我加的计数器实测单槽时为 **29.00 次/步**。

但**只修单槽时实测仍是 29.00**。第二个原因：`am_slope = anchor_am − previous_am` 在每次 `_integrate_structure` 调用时重新构造，M1b 的载荷作用 memo 以 `id(slope)` 为键 ⇒ 每趟重建 10 个 action、10 个新 `data_ptr` ⇒ **无论多少槽都全 miss**。修掉后才落到 **10.33 次/步**。

同一 30 步窗口、只改一处：

| 配置 | 分解/步 | 步价 |
|---|---|---|
| `FLUXV_LU_CACHE=0` | 104.87 | 4.675 s |
| `=1` 单槽（干预前） | 29.00 | 2.966 s |
| `=1` 按 β 的桶，`am_slope` 未修 | 29.00 | 2.863 s |
| `=1` 按 β 的桶 + `am_slope` memo | **10.33** | **2.406 s** |

一处我第一版做错、由测量纠正：`inverse_beta_dt2` 必须在内键（它是子步长的函数、子步长是 β 的函数，每趟 10 个值）；放进外键会**完全复现单槽**（实测仍 29.00）。

验收：30 步 `torch.equal(cn)`；80 步 digest 链 cache on/off 全等；80 步 `cache=0` 与**改动前树**全等；parity 6/6。默认已翻 `=1`，`=0` 保留逃生。

## 3. S3：两个子项都被实测否证

### 3.1 位掩码延迟有限性检查：零收益

这套基础设施在前一轮已落地并实测：**2.081 → 2.087 s/步（0.000，且略差）**。现在的原因也测到了：那些 `wp.synchronize_device` **自身**时间只有 0.002 s/步——它们在等真实 GPU 工作，延迟它们只是把等待挪到下一个同步点。S2b 的 backlog=0 进一步佐证。

另外，计划里的 "`~1,663` 次/步 `wp.synchronize_device`" 与我插桩得到的数不一致：我数到 **3,641 次 `Tensor.item` + 2,909 次 `wp.synchronize_device` = 6,550 次阻塞式主机读取/步**（测得等待 3,426.7 ms/步，**包含**它所等待的 GPU 工作，因此是上面相位时间的分解，**不能相加**——我第一版相加得到 159% 的假闭合，已修）。

### 3.2 冻结端点环几何缓存：前提错，零命中

实现方式：按 `(velocity 对象, include_mf21)` 记忆整个 `velocity_force`，**逐位正确但零命中** —— `surface_evaluate` 调用 179.97 → **179.00** 次/步，步价 2.406 = 2.406。

原因在 `q16_flux_v5m_native_fsi.py:578`：第二对调用用的不是同一个 velocity：

```python
average_velocity_t = 0.5 * (wp.to_torch(velocity) + wp.to_torch(predictor.velocity))
average_velocity = wp.from_torch(average_velocity_t, ...)   # 新对象
```

每子步 4 次调用的输入两两不同，没有可复用的重复。已撤回该改动。

真正剩下的冗余**只在状态侧**（`structural_state` 是冻结的）：3 次 state 插值 + `assemble_native_ring_geometry` 中由 state 决定的那一半。实测拆分：`surface_evaluate` 145.6 ms/步，其中 `assemble_native_ring_geometry` **75.9**，插值为 69.7 的残差 ⇒ 可缓存部分 **≤73 ms/步（1.3%）**，而拿到它必须把 `assemble_native_ring_geometry` 拆成状态侧/速度侧，属有逐位风险的中间层重构。

### 3.3 我另做的两项（不在计划里）

- **S3a** `repeated_linearization` 按批宽缓存：逐位，但只 **0.6%**（135 ms/次刷新 ≈ 17.5 ms/步）。且**批宽杠杆不存在**：47 / 35 / 28 批的墙钟 **10.80 / 10.83 / 10.81 s**，切线逐位相同 ⇒ 刷新成本是每列算子作用的**吞吐**（3.63 ms/列），不是启动开销。
- **S3c** 试探态线性化只算"会抛异常的部分"：`_current_fields` 只有两处会抛（`_strain` 内的几何闸门、`_alpha` 内的有限性检查），而 `_projected_b` **一处都不抛**却是 **75%** 的成本（546.1/724.4 ms/步）。改为 `validity_only_prechecked` 后 **异常面按构造相同**，实测 **150 步 5.630 → 5.346 s/步（1.053×，−0.284 s/步）**，且 30/80/150 步 digest 链全部逐位相同，注入测试 4/4（坍缩态两条路径抛同一消息；压缩扫描 1.0/0.5/0.1/0.02/0.0 判断一致）。
  **这一项（5.0%）比计划 S3 的两项预期都大，而且它是逐位的。**

## 5. S5：规格需要重写（实测推翻三处前提）

1. **环诱导侧完全没被覆盖。** `ring_BS` 实测 **800.0 ms/步（47.95 次重启动/步）**，位于 `kernels_ring_velocity.py`，**完全没有远场分支**。而 9.63e9 的对数台账只覆盖粒子侧。按耗时算环侧是气动侧的 **43%**。
2. **`rho > 12.0` 的早退是逐对判断，且在整核 fp64 内。** 每个远对仍要算 fp64 的 `sqrt`、`rho`、`w = c⁻¹/4π · 1/(r²r)`（`pfield_torch_gpu.py:51`）。要做"远场 fp32"，需要单独的 fp32 代码路径**以及** `pos/gamma/sigma` 的 fp32 副本（`_require_tensor` 目前强制 host 输入为 fp64）。
3. **不存在"远块"。** 源块是按**生成序**连续切分（`start = b*block_size`），没有空间排序；混合精度要按块判断就得先有 Morton/bbox 排序。
4. 计划里"单对 0.53 → 0.03–0.06 ns"的目标：我测到的机器锚点是 `2436²` fp64 `dgetrf` 21.65 ms = **445 GFLOP/s 实效**，`lu_solve` 0.60 ms；粒子侧实测每对 **≈0.53 ns**（源自 5.2 s/步 ÷ 9.63e9 对）。

## 10. 需要你改计划的四处

**① S3 的两项都要撤。** 位掩码：实测零收益（且 backlog=0 说明同步在等真实 GPU 工作）。冻结环几何：前提错（第二对用新造的 `average_velocity`），零命中，真实上限 1.3%。

**③ A5 的 `ΔSt ≤ 0.08` 判据不能用单一 `dominant_St`。** 实测：同一批数据里两个 run 都同时含 **0.3887 与 0.4442** 两个峰，HEAD 的幅度比 **1.09**（几乎并列）、旧的是 1.37；换窗口两者又都选 0.4541 / 0.4992。payload 里那一位的翻转由 9% 的幅度差决定，而位移量恰好等于一个 FFT bin（ΔSt = 1/18 = 0.0556）。**判据应改为前两峰幅度比或整谱比较。**

**④ 长跑预算必须用"尾迹填满后"的速率。** 全长平均 **6.999 s/步** vs 150 步窗口 **5.35 s/步**（短窗低估 31%）：尾迹行数线性增长（末态 9,000 环 = 300 行），环诱导成本 ∝ 行数。A5/L1/L4 的排期按 6.999 s/步 而不是 5.35 s/步 算。
